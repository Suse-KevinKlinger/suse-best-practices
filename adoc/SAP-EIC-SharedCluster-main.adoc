[#istioInstall]
== Installing {istio}

Even though {istio} is available for deployment using the {rancher} Apps, we recommend to use the {rac}.
The {istio} chart can be found at https://apps.rancher.io/applications/istio.

// IMPORTANT::
// SUSE does not offer application support for {istio}.
// For support requests, contact link:https://istio.io/[Istio].
// TODO: when available, add information from SAP regarding to shared cluster.
// TODO: when available, double-check that link includes istio as a requirement and
//       add additional links if necessary

Before deploying {istio}, ensure that the requirements described at https://me.sap.com/notes/3247839 are met.

To deploy the chart, create the related namespace and *imagePullSecret* first.
To create the namespace, run:

[source, bash, subs="attributes"]
----
kubectl create namespace {istio_namespace}
----

[#istioIPS]
Instructions how to create the *imagePullSecret* can be found in <<imagePullSecret>>.

[#istioLIR]
Before you can install the application, you need to log in to the registry.
You can find the instructions in <<LoginApplicationCollection>>.

NOTE: The *{istio_namespace}* namespace, *imagePullSecret*, and registry login established for {istio} will be reused by:
{kiali} at <<kialiInstall>>, {prometheus} at <<prometheusInstall>>, and {grafana} at <<grafanaInstall>>. 

== Deploying the chart

Create a file _values.yaml_ to store some configurations for the {istio} Helm chart.
The configuration might look like the following:

[source, yaml]
----
global:
  imagePullSecrets:
    - name: application-collection
----

To install the application, run:

[source, bash, subs="attributes"]
----
helm install istiod oci://dp.apps.rancher.io/charts/istio \
-f values.yaml \
--namespace={istio_namespace} \
--version {istio_chart_version}
----

For more information on installing and configuring {istio}, check the reference guide at https://docs.apps.rancher.io/reference-guides/istio/.
// end::istio-installation[]

    custom_metrics_url: http://prometheus-server.istio-system
    url: http://prometheus-server.istio-system

[#raNamespaceConfig]
== Configuring Restricted Access for Kubernetes Clusters

This section describes how to set up Restricted Access for Kubernetes Clusters, an operating model where {elm} and {eic} are granted only the minimum necessary permissions required for their operation. For more details on Restricted Access for Kubernetes Cluster option, refer to https://help.sap.com/docs/edge-lifecycle-management/documentation/key-concepts#kubernetes-cluster-access-options.

NOTE: {elm} supports namespace customization, which is especially useful when deploying multiple {eic} instances on the same Edge Node. The names used in this section (`edgelm`, `istio-gateways`, and the `edge-icell` namespace along with its prefixed variants) reflect the default values provided in the {elm} UI. If you customize them during deployment, ensure you use your custom names in the subsequent commands.

The configuration is divided into two stages to align with the deployment flow:

1. **Phase 1: Access Provisioning for Edge Node Initialization:** Applying initial security policies and setting up a restricted user in Rancher to initialize the Edge Node.
2. **Phase 2: Access Provisioning for {eic} Deployment:** Applying solution-specific policies and granting permissions for {eic} when the deployment is "Prepared".

To fulfill the infrastructure requirements, refer to https://me.sap.com/notes/3247839.

[NOTE]
====
**For Edge Integration Cell versions older than 8.48:**
You must manually apply the resources or use legacy RBAC binding methods. Refer to <<legacyRestrictedAccess>> in the Appendix for specific legacy provisioning steps.
====

[#raPhase1]
=== Phase 1: Access Provisioning for Edge Node Initialization

When the **Restricted Access to Kubernetes Cluster** option is enabled during Edge Node creation, the {elm} UI will prompt you to download the required Kubernetes resources. Refer to the official SAP documentation for more details: https://help.sap.com/docs/edge-lifecycle-management/documentation/initializing-edge-node.

Extract the downloaded file to a dedicated directory, for example, `restricted-elm`. The archive includes a script named `apply-restricted-resources.sh`. Make the script executable and run it to apply the foundational security policies required by {elm}:

[source, bash]
----
cd restricted-elm
chmod +x apply-restricted-resources.sh
./apply-restricted-resources.sh
----

[#raIPSPhase1]
==== Configuring ImagePullSecrets for {elm}

Since the target ELM namespace is enabled for Istio sidecar injection, it requires an *imagePullSecret* from the SUSE Application Collection. For detailed instructions, refer to <<imagePullSecret>>.

[source, bash]
----
kubectl create secret docker-registry application-collection -n edgelm \
  --docker-server=dp.apps.rancher.io \
  --docker-username=<yourUser> \
  --docker-password=<yourPassword>
----

[#createRestrictedUser]
==== Creating the restricted user in Rancher

You must create a dedicated restricted user in Rancher. {elm} uses this identity to securely connect to your cluster without requiring broad administrator privileges.

1. In Rancher, go to **Users & Authentication** > **Create**.
2. Set the user name (for example, `eic-restricted`) and select **Standard User**.
3. Record the **User ID** (formatted as "u-XXXXX") and **password** for the subsequent configuration steps.
4. Assign the user to the downstream cluster with **Cluster Permission > Custom > View Nodes**.

image::SAP-Rancher-Main-Users.png[title=Rancher user id listed,scaledwidth=99%]

image::SAP-Rancher-Main-Users-Add-ClusterMembership.png[title=Rancher assign user membership,scaledwidth=99%]

[#raUserConfigPhase1]
==== Granting restricted user permissions for {elm}

In this section, we associate the restricted user created in the previous step with the security policies. This binds the Rancher user to the exact rights required by {elm}, following the principle of least privilege. 

Create a file named `bind-elm-rbac.sh` and add the following script:

[source, bash]
----
#!/bin/bash
set -eu

if [ "$#" -ne 2 ]; then
  echo "Usage: $0 <USER_ID> <ELM_NAMESPACE>"
  echo "Example: $0 u-abcde123 custom-edgelm"
  exit 1
fi

USER_ID="$1"
ELM_NAMESPACE="$2"

PAYLOAD=$(printf '[{"op":"add","path":"/subjects/-","value":{"apiGroup":"rbac.authorization.k8s.io","kind":"User","name":"%s"}}]' "$USER_ID")

echo "Binding ELM RoleBindings and ClusterRoleBindings for user: $USER_ID in namespace: $ELM_NAMESPACE"

# 1. RoleBindings
TARGET_ROLES=("rb-edgelm-manage" "rb-edgelm-admin")

for RB_NAME in "${TARGET_ROLES[@]}"; do
  if kubectl get rolebinding "$RB_NAME" -n "$ELM_NAMESPACE" >/dev/null 2>&1; then
    EXISTING=$(kubectl get rolebinding "$RB_NAME" -n "$ELM_NAMESPACE" -o jsonpath="{.subjects[?(@.name=='$USER_ID')].name}" 2>/dev/null || true)
    
    if [ "$EXISTING" == "$USER_ID" ]; then
      echo "  Skipping $RB_NAME in namespace $ELM_NAMESPACE (User already bound)"
    else
      echo "  Patching $RB_NAME in namespace $ELM_NAMESPACE..."
      kubectl patch rolebinding "$RB_NAME" -n "$ELM_NAMESPACE" --type=json -p "$PAYLOAD"
    fi
  else
    echo "  Skipping $RB_NAME (Not found in namespace $ELM_NAMESPACE)"
  fi
done

# 2. ClusterRoleBindings
CRB_LABEL_FILTER="-l edgelm.sap.com/product=edgelm,edgelm.sap.com/cleanup=edgelm"
TARGET_CLUSTER_ROLE_PREFIX="crb-edgelm-cluster-admin"

FOUND_CRBS=$(kubectl get clusterrolebindings $CRB_LABEL_FILTER -o name 2>/dev/null | grep "$TARGET_CLUSTER_ROLE_PREFIX" || true)

for CRB in $FOUND_CRBS; do
  CRB_NAME=$(basename "$CRB")
  EXISTING=$(kubectl get clusterrolebinding "$CRB_NAME" -o jsonpath="{.subjects[?(@.name=='$USER_ID')].name}" 2>/dev/null || true)
  
  if [ "$EXISTING" == "$USER_ID" ]; then
    echo "  Skipping $CRB_NAME (User already bound)"
  else
    echo "  Patching $CRB_NAME..."
    kubectl patch clusterrolebinding "$CRB_NAME" --type=json -p "$PAYLOAD"
  fi
done

echo "User permission binding for ELM complete."
----

Make the script executable and run it with your `<USER_ID>` (configured in the section <<createRestrictedUser>>) and your ELM namespace. 

Example:
[source, bash]
----
chmod +x bind-elm-rbac.sh
./bind-elm-rbac.sh u-qsj27 edgelm
----

2. Navigate to the target cluster.
3. Download the kubeconfig file.

=== Phase 2: Access Provisioning for {eic} Deployment

When the Edge Node is "Available", initiate the {eic} deployment in the {elm} UI. When the solution reaches the **Prepared** state, return here to apply the specific solution resources.

IMPORTANT: For multi-instance deployments, before deploying a second {eic} instance on the same cluster, ensure you have an available IP address set to the {metallb} `IPAddressPool` so it can be assigned to the Istio ingressgateway deployed by {eic}. For more details, refer to <<metalConfig>>.

Download the second zip from the {elm} UI. The filename depends on the solution name configured in the UI. For example, for a solution named "Edge Integration Cell Example", the file will be `restricted-resources-Edge_Integration_Cell_Example-<x.y.z>.zip`. Extract it to a directory, e.g., `restricted-eic`. As in Phase 1, make the included deployment script executable and run it:

[source, bash]
----
cd restricted-eic
chmod +x apply-restricted-resources.sh
./apply-restricted-resources.sh
----

This action creates the necessary namespaces for {eic} and applies the required security policies for the solution components.

[#raIPSPhase2]
==== Configuring ImagePullSecrets for EIC namespaces

The previous step generated the solution-specific namespaces (e.g., `istio-gateways`, `edge-icell`, `edge-icell-services`, `edge-icell-secrets`, and `edge-icell-ela`). With the exception of the secrets namespace, all of these namespaces require an **imagePullSecret** to authenticate against the registry. For detailed background instructions, refer to <<imagePullSecret>>.

You can automate the creation of these secrets by creating a file named `create-eic-ips.sh` with the following content:

[source, bash]
----
#!/bin/bash
# Update the array below with your customized namespaces if applicable
NAMESPACES=("istio-gateways" "edge-icell" "edge-icell-services" "edge-icell-ela")

for ns in "${NAMESPACES[@]}"; do
  kubectl create secret docker-registry application-collection -n $ns \
    --docker-server=dp.apps.rancher.io --docker-username=<yourUser> --docker-password=<yourPassword>
done
----

Remember to replace `<yourUser>` and `<yourPassword>` with your actual registry credentials inside the script before executing it:

[source, bash]
----
chmod +x create-eic-ips.sh
./create-eic-ips.sh
----

==== Granting restricted user permissions for {eic}

Just as in Phase 1, <<raUserConfigPhase1>>, you must bind the restricted Rancher user to the newly generated solution-specific policies. 

Create a file named `bind-eic-rbac.sh` and add the following script:

[source, bash]
----
#!/bin/bash
set -eu

if [ "$#" -lt 2 ]; then
  echo "Usage: $0 <USER_ID> <NAMESPACE_1> [<NAMESPACE_2> ...]"
  echo "Example: $0 u-abcde123 edge-icell edge-icell-services edge-icell-secrets edge-icell-ela istio-gateways"
  exit 1
fi

USER_ID="$1"
shift
NAMESPACES=("$@")

PAYLOAD=$(printf '[{"op":"add","path":"/subjects/-","value":{"apiGroup":"rbac.authorization.k8s.io","kind":"User","name":"%s"}}]' "$USER_ID")

echo "Adding EIC RoleBindings for user: $USER_ID in namespaces: ${NAMESPACES[*]}"

TARGET_ROLES=("rb-edgelm-manage" "rb-istio-gateways-admin" "rb-admin" "rb-app-admin")

for NAMESPACE in "${NAMESPACES[@]}"; do
  echo "Processing namespace: $NAMESPACE"
  
  for RB_NAME in "${TARGET_ROLES[@]}"; do
    if kubectl get rolebinding "$RB_NAME" -n "$NAMESPACE" >/dev/null 2>&1; then
      
      EXISTING=$(kubectl get rolebinding "$RB_NAME" -n "$NAMESPACE" -o jsonpath="{.subjects[?(@.name=='$USER_ID')].name}" 2>/dev/null || true)
      
      if [ "$EXISTING" == "$USER_ID" ]; then
        echo "  Skipping $RB_NAME (User already bound)"
      else
        echo "  Binding $RB_NAME..."
        kubectl patch rolebinding "$RB_NAME" -n "$NAMESPACE" --type=json -p "$PAYLOAD"
      fi
    fi
  done
done

echo "User permission binding for EIC complete."
----

Make it executable and run it with your `USER_ID` (configured in the section <<createRestrictedUser>>) and your EIC namespaces.

Example:
[source, bash]
----
chmod +x bind-eic-rbac.sh
./bind-eic-rbac.sh u-qsj27 edge-icell edge-icell-services edge-icell-secrets edge-icell-ela istio-gateways
----

When the permissions are successfully bound, return to the {elm} UI and click **Resume deployment**.
